A penetration test report usually arrives as a PDF with a severity chart on page two. The chart is a poor guide to what to do. Reading the report well is a separate skill from commissioning it.

## Ignore the headline severity first

Severity in a report has been calculated for a generic reader. Your system is not generic. Read each finding's evidence and ask three questions:

1. Is the affected component reachable from the internet, or only from an internal network?
2. What access does exploitation require — anonymous, a standard user, an administrator?
3. What is the actual data behind it, and is that data sensitive in your context?

An issue marked high in a service that holds only public reference data ranks below a medium in the authentication path. This is not a reason to dismiss the high finding; it is a reason to sequence deliberately.

## Check the evidence before the recommendation

A finding without a reproducible request is a hypothesis. Reproduce it, or ask the assessor to demonstrate it. Most good reports include the request, the response and the state that made it possible.

Where reproduction fails, find out why. It is usually one of three things:

- The environment differs from the one tested.
- The test account had permissions a real user would not have.
- The finding was generated by a scanner and not validated by hand.

Only the third is a problem with the assessment. The first two are useful information about your environments.

## Read the fix as a design question

Remediation advice is written against the observed implementation, which makes it a starting point rather than an instruction. A recommendation to "add authorization checks in the handler" may be correct and still be the wrong fix if authorization belongs in one place rather than twelve.

Take each recommended fix and ask where the corresponding control should live. If the answer is "everywhere", the architecture is the finding.

## Look for what is missing

Reports describe what was found, not what was not. Read the scope section carefully for what was excluded: authenticated areas, specific API versions, mobile clients, third-party integrations.

An assessment that quietly excluded the half of the system you were most worried about is not a clean bill of health.

## Close the loop with a retest

Remediation is complete when the specific exploit no longer works, not when the ticket is closed. Where a fix is structural — moving authorization into a middleware layer, for example — the retest should attempt the bypass, not only the original request.

## A short checklist

- Reproduce every finding before scheduling work.
- Rank by reachability and data sensitivity, not severity alone.
- Ask where each control belongs.
- Read the exclusions.
- Retest the exploit, and attempt the variant.

A report is a set of arguments. Treat it the way you would treat a design review: with interest in the reasoning and a willingness to disagree.
